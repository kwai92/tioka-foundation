## 2. 备份恢复演练步骤（F-11 §3.8）

前置：练习环境具备 PostgreSQL 客户端与 Docker；源环境与恢复环境相互隔离。

1. 记录演练开始时间与源库当前时间点。
2. 以属主账号导出两库（**同一时间点**，命令见 `deploy/README.md` §7）：
   - `pg_dump -Fc -U fdn_owner -h <host> -d foundation -f foundation-<yyyymmdd>.dump`
   - `pg_dump -Fc -U fdn_owner -h <host> -d keycloak   -f keycloak-<yyyymmdd>.dump`
3. 导出一致的对象存储快照与主密钥（主密钥经 KMS 包裹）。
4. 在隔离环境恢复两库（`pg_restore`），核对两库时间点一致。
5. 重放对象存储归档，核对审计归档可读。
6. 启动 Foundation 与 Keycloak，触发/等待一次**账号对账**（BAS-03），记录修复条数。
7. 记录演练结束时间，计算实测 RTO / RPO。
8. 复核人确认：两库时间点一致、账号对账通过、审计链完整。

## 3. 升级与回滚演练步骤（F-11 §3.9）

前置：演练版本 `N` 已在线；新版本 `N+1` 已构建并推送镜像。

1. 记录升级前版本号与库表基线。
2. 升级前**强制备份**（见 §2 步骤 2）。
3. 执行 `helm upgrade --install foundation deploy/helm/foundation -n foundation --create-namespace -f deploy/helm/foundation/values-prod.yaml --wait`。
4. 等待迁移 Job：`kubectl -n foundation wait --for=condition=complete job/foundation-migrate --timeout=10m`。
5. 校验应用就绪（`/actuator/health/readiness`）与关键业务冒烟。
6. **回滚**：把应用镜像换回版本 `N`（`helm upgrade ... --set image.tag=<N>` 或回滚到上一 Release），
   确认旧代码能在新库上运行（「先扩后收」）。
7. 若涉及破坏性迁移（删列/删表/收权限），回滚只能从 §2 的备份恢复，记录恢复耗时。
8. 记录结论与遗留问题。
